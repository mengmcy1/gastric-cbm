   不得混入正式 400 次 bootstrap。

## 7. 当前工程运行与冻结正式恢复方案的差距

冻结正式入口为：

```text
程序/SAE/正式代码/run_clong_rpa_development.sh
```

正式 runner 不只是启动 bootstrap worker，还依次负责：

1. GPU 与参数预检；
2. 创建或验证 `run_code_snapshot.json`；
3. 运行回归测试；
4. 从新根执行 seed43/44 development 训练；
5. 准备 seed42/43/44 分析 cache；
6. 执行 full-train matching，并检查 strict-anchor 闸门；
7. 以 fail-fast 方式监督所有 bootstrap worker；
8. coordinator 唯一归并 index 0–399 并冻结门槛；
9. 执行 val reproduction；
10. 运行最终 development-calibration 判定与产物固结。

冻结恢复记录要求第二次正式运行使用新的
`结果/SAE/RP_A_Development_20260825_retry1/`，从 seed43/44 训练开始完整重跑，不能复制或续写
首轮 checkpoint、matching 或 bootstrap records。运行快照必须绑定 development root、GPU 列表、
`source_block=32` 和 `target_block=128`。

四卡本身不是统计协议违规：冻结协议允许按实际 GPU 数设置 `worker_count`，并以
`replicate_index % worker_count == worker_rank` 静态分工。当前 v2 不合规的真正原因是：

- 直接复制 probe cache；
- 绕过正式 runner 与 code provenance；
- 没有重新训练 seed43/44 和 full-train matching；
- 没有 strict-anchor 闸门、coordinator、val reproduction 和 finalizer；
- 独立 tmux worker 不具备冻结 runner 的任一失败即停止其余 worker的 fail-fast 行为；
- 使用的是 probe 环境和手工输出根，而不是固结后的正式恢复血缘。
