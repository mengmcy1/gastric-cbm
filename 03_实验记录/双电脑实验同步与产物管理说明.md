# 双电脑实验同步与产物管理说明

## 1. 目的与适用范围

本仓库同时维护两条互不混淆、但共享统一评价协议的实验线：

1. 自研 Framework：继续验证显露补全与补充高斯能否支撑水平总视角 30°（中心左右各 ±15°）。
2. InfiniSplat 对照复现：先复现官方 RGB 单图流程，再把冻结 PLY 接入相同的 `true_arc` 5°/15°/30° 协议。

两台电脑共用同一个 Git 仓库。Git 用来同步代码、配置、文档和小型证据，不用来镜像全部 `outputs/`。电脑上是否存在某个大型输出，只表示该电脑能否立即复核，不改变已经记录并有哈希支撑的实验事实。

## 3. 产物分为三层

### 3.1 必须通过 Git 同步

- 正式脚本、配置、输入清单和补丁；
- 实时进度与方案文档；
- `records/` 中的小型 JSON、CSV、环境锁定信息、完整性结果和人工评分；
- 能唯一指向大型产物的清单：运行 ID、相对路径、字节数和完整 SHA256。

### 3.2 按里程碑选择性传输

- 已冻结、准备接入下一阶段的 PLY；
- 等待另一台电脑或用户人工播放的最终 MP4；
- 无法重新下载且确实需要复核的关键模型或中间结果。

这类文件不提交 GitHub。使用局域网、移动硬盘或其他大文件传输方式复制；复制后必须用清单中的字节数和 SHA256 校验。

### 3.3 仅保留在产出机器

- 全部逐帧 RGB、Depth、Alpha、掩码和 NPY；
- dry-run、失败运行、诊断缓存、联系表和临时日志；
- 可从脚本重新下载的 checkpoint；
- 未冻结的候选 PLY 和视频。

这些内容继续放在各实验的 `outputs/`、`models/`、`logs/` 或 `99_过程文件_可删除或归档/` 中，并由 `.gitignore` 排除。

## 4. 每次换电脑前后的固定流程

### 4.1 开始实验前

```bash
git status -sb
git pull --ff-only
```

然后按顺序检查：

1. 阅读本说明、`AGENTS.md` 和当前实验线的进度文档；
2. 查看对应 `records/README.md` 是否仍有“待同步”项目；
3. 核对本机所需模型、冻结输入和大型产物是否存在，并校验哈希；
4. 本机缺少大型产物时，先判断能否重跑或重新下载；只有无法接受重算成本且确需复用时才传输大文件。

不得因为本机 `outputs/` 为空，就把已完成实验改写成“未完成”；应记录为“实验已完成，本机产物未同步”。

### 4.2 完成一次正式运行后

1. 使用新的唯一运行目录，不覆盖同名旧输出；
2. 记录源码 Git commit、外部源码 commit、运行 ID、配置、输入哈希、环境和硬件；
3. 记录候选冻结产物的相对路径、字节数、完整 SHA256、帧数或高斯数量；
4. 将小型汇总、自动指标、人工评分和完整性检查复制或整理到对应 `records/`；
5. 更新对应实验线的实时进度文档；
6. 执行 `git status`，确认没有误提交模型、视频、PLY 或逐帧输出；
7. 提交并推送，另一台电脑开始工作前执行 `git pull --ff-only`。

## 5. 命名、冲突与冻结规则

- 运行目录名必须包含样本、阶段、用途、版本和日期，例如 `P01_stage01_true_arc_formal_v4_fallback_20260807`；必要时再追加机器简称。
- 同名运行的哈希不同，说明它们不是同一个产物。保留两份并分别登记，不得覆盖或选一份冒充另一份。
- 正式比较前必须冻结某一份 PLY/视频，以完整 SHA256 为身份，不以“最新文件”或本机绝对路径为身份。
- 文档只写仓库相对路径；盘符、用户名、Conda 安装位置和显卡型号属于机器环境字段。
- `records/` 只保存可读、可审计的小型证据，不保存 PLY、MP4、checkpoint 或逐帧图像。

## 7. 另一台电脑拉取本次提交后的待办

1. 不移动、不删除现有 `outputs/`；先确认当前分支与 Git 状态干净。
2. 按自研 `records/README.md` 提升 v4 的正式汇总、指标和人工评分。
3. 按 InfiniSplat `records/README.md` 生成或复制 P01 官方冒烟的产物清单、运行汇总、环境和视频完整性记录。
4. 确保清单使用完整 SHA256；不得把进度文档中的省略哈希直接填入。
5. 更新两个 `records/README.md` 的同步状态和日期，提交并推送。
6. 当前电脑拉取并核验这些小型记录后，再开始自研补全模型对比或 InfiniSplat `true_arc` 适配。

暂不引入 DVC 或新仓库。只有当冻结大产物数量持续增加、手工清单和选择性传输已经成为稳定瓶颈时，再评估对象存储或 DVC。
